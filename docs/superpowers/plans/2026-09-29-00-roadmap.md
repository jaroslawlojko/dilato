## Carried from plan 1 (read before writing plans 2 and 3)

**Installed versions:** Expo SDK 57, React Native 0.86, React 19.2, TypeScript 6, Jest 29 (`jest-expo` 57). Install anything new with `npx expo install`. TypeScript 6 does not auto-include `@types/*`: `app/tsconfig.json` lists `"types": ["jest", "node"]`; split a test-only tsconfig when UI code lands.

**Carried from plan 2 (read before writing plan 3):**

1. Open the database once with `openAppDb()` (`src/data/drivers/expo.ts`); it migrates. All challenge actions go through `createChallengeService({ db, userId, newId })` — never call domain transitions and repositories separately. `newId` = `randomUUID` from `expo-crypto` (`npx expo install expo-crypto`).
2. Until plan 4 adds accounts, `userId` is a local UUID generated once and kept on the device; plan 4 must re-key local rows to the auth user id on first registration.
3. Call `service.open(new Date())` on launch, on foreground and on each timer tick that crosses `targetAt`; render from the returned `Snapshot`. `snapshot.awarded` drives celebrations (`celebrationTier`); `snapshot.pendingConfirmation` must be answered (`confirmSucceeded` / `confirmSmokedEarlier`) first: until then `start`, `addOvertime`, `finishForToday`, `interrupt` and `startCraving` reject with `DomainError('confirmation_pending')`, so show the "Nadal trwa?" sheet whenever it is set. While the timer screen is visible, call `markSeen(visibleSince, now)` on each tick, where `visibleSince` is when the screen last became visible (foreground + focused); a goal the screen watched arrive counts as seen, one reached before the screen appeared waits for the answer.
4. A rejected action rejects with `DomainError` and writes nothing — show it calmly (spec §8). `NoProfileError` means onboarding has not saved a profile. `InvalidRowError` means a stored row breaks the data model (writes validate, so this needs a bad migration or bad sync data): every service call will fail the same way, so show a calm recovery state and report it to Sentry without row contents.
5. Profile writes: `db.transaction((tx) => saveProfile(tx, userId, profile, new Date()))`. Invalid values throw `InvalidRowError` naming the column. `bestSmokeFreeMinutes` is managed by the service; S10 reads `snapshot.bestSmokeFreeMinutes` for unlocks.
6. Suggestions: `availableSuggestion(suggestNext(snapshot.challenges.filter(isClosed), profile.cigsPerDay, plannedForTomorrow), now)`. The S09 "plan na jutro" is not stored yet — plan 3 decides where (profile column or local table).
7. Not provided: overtime arc progress and remaining seconds (derive from `overtimeBlockStartedAt` / `targetAt`); an open challenge is an `empty` row in `timelineRows`.
8. Plan 4: the outbox payload is the SQLite row (booleans 0/1, UTC ISO strings with milliseconds) — map it for Postgres. Pulled rows must **not** go through `writeRow`: it stamps local `updated_at`, forces `deleted_at = null` and queues an outbox entry (pulled rows would bounce back to the server). Add an `applyRemoteRow` that normalises to the stored format, validates with the `rows.ts` mappers, keeps the remote `updated_at` / `deleted_at`, applies last-write-wins, whitelists columns per table and skips the outbox; merge `badges_earned` on `(user_id, badge_id)` (not `id`) by min(first)/max(times), and `profiles.best_smoke_free_minutes` by max. Soft deletes also need a `writeRow` variant that sets `deleted_at`.

**Deferred from the plan 2 review (not yet filed as issues):**

- **Needs the owner's decision.** The best smoke-free value depends on when the app was opened: opening it on the evening before the 04:00 rollover can unlock the 24 h benefit, while opening it only the next morning does not. Option: record the live value at the rollover moment.
- `db.ts`: a failing `ROLLBACK` hides the original error and can wedge the connection. Wrap it in try/catch and rethrow the original.
- `Db` is assignable to `Tx`, so calling `db` inside a transaction deadlocks silently. Brand `Tx`.
- `rows.ts` accepts impossible dates (`2026-02-30`, day `2026-13-45`). Require that the value round-trips through `toISOString`.
- A coalesced outbox entry has no version. Plan 4 must delete an entry only if its payload `updated_at` still matches the one it sent.
- A craving session can outlive its challenge, or stay open when a second session starts. End it on close / restart.
- `package.json` has no `engines` field, but the tests need Node ≥ 22.5 (`node:sqlite`).

**Open decisions for plan 3 (owner):**

- S12 colours: `timelineRows` never marks an interrupted attempt as `record`, while the record statistic and the "Nowy rekord" badge do count it; a multi-day challenge is drawn only on its start day.
- Threshold badges are not awarded while a challenge is still running (a 24 h challenge at hour 13 has not yet earned the 12 h badge) — decide whether S05 should award them live.
- A first challenge started late in the evening with the default "22:00 yesterday" answer starts with ≥ 24 h smoke-free; the morning sheet should handle evening starts.
- Template leftovers to replace: `App.tsx`, `index.ts`, `app.json` / `package.json` name and slug `app`, default icons; bundle ids in plan 6.
